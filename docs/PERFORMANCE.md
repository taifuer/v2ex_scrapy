# 性能基线与验证

## 测量方式

```bash
cd analysis/v2ex-analysis
npm run build
npm run test:budget
npm run test:performance
```

工具仅在 `127.0.0.1` 临时托管 `dist`，使用 gzip、全新浏览器上下文和关闭的浏览器缓存。模拟 390×844 视口、1.6 Mbps 下载、150 ms 延迟和四倍 CPU 降速，每个页面重复三次。输出默认写入忽略的 `test-results/performance.json`；可用 `PERFORMANCE_OUTPUT`、`PERFORMANCE_RUNS` 覆盖。

“主内容就绪”指目标统计区出现，或图表 canvas 已绘制非空彩色内容，包含自动检查的开销。传输量仅统计该时点已完成的请求，不是浏览整个页面后的总下载量。这是本地实验基线，不是线上测速、真实手机性能、LCP 或 INP。线上评估仍需区分网络、设备与缓存条件。

关键词详情调整前约为 699 KiB。优化没有减少统计内容：主趋势不再等待下方代表评论加载完成；需要图表的页面将 ECharts 下载与数据请求重叠，纯文本/月度页面仍不预载 ECharts。小幅时间差可能来自实验波动，不应解释为所有设备都具有同样收益。

## 内存与交互

连续选择 30 个关键词后，再浏览相同 30 个关键词，每 10 次选择强制 GC 读取 JS 堆：调整前后第二轮均稳定在约 37–38 MiB。尚未发现该路径持续增长的证据，暂不添加复杂的多层缓存淘汰机制；这个实验不覆盖全部页面，也不证明完全没有内存问题。

主应用的图表实例通过 `chartRegistry.ts` 管理。页面切换时清理已脱离 DOM 的实例，销毁应用时全部释放，返回视图时重新初始化；独立视图保留自身的卸载清理。趋势提示框复用 `chartTooltip.ts`，窄屏单列、限制宽高，保留长名称换行及文本转义。详情选择器支持键盘选项自动滚入可见区。

回归验证包括：慢评论分片不阻塞主趋势、断开 DOM 后图表释放、320px 窄屏 Top 30 提示框不溢出且可滚动、详情选择器键盘操作，以及原有桌面与移动端流程。后续比较应使用同样的构建数据、限速和测试流程，而不是只比较 JS 文件大小。
