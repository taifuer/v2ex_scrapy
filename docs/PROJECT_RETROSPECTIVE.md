# V2EX 看板项目复盘

本文复盘截至 2026-08-14 的项目演进，重点不是罗列功能，而是总结如何把一个论坛爬虫逐步建设为可验证、可追溯到原始内容、可静态部署的数据分析产品，并提炼可复用于其他论坛、社区或群聊数据项目的方法。当前实现细节见 [技术架构与功能实现](ARCHITECTURE.md)，指标和结论见 [数据分析说明](DATA_ANALYSIS.md)。

## 1. 项目背景与重构边界

本项目基于 [oldshensheep/v2ex_scrapy](https://github.com/oldshensheep/v2ex_scrapy) 继续维护。2023 年版本已经具备 Scrapy 爬虫、SQLite 存储、主题/评论/成员模型，以及一个 Vue/Vite 早期页面。原分析脚本主要通过若干 SQL 直接导出月度数量、标签使用量和 Top 20 榜单，前端仍接近 Vite 模板项目。

2026 年的工作保留了已有爬虫框架和基础数据模型，并围绕数据可靠性与分析产品化展开系统性重构。核心新增包括抓取补全、历史数据治理、离线分析层、时间动态分析、实体详情、标题关键词、URL 状态化、静态分片加载、统一可视化、移动端适配、测试体系及生产部署。2026-07-05 至 2026-08-14 的持续迭代，完成了从基础统计页面到完整社区数据产品的演进。

## 2. 起点与最终形态

| 维度 | 早期状态 | 当前状态 |
| --- | --- | --- |
| 抓取 | 顺序扫描主题 ID，已有记录多直接跳过 | Cookie/代理配置、指定区间与离散 ID、幂等更新、分页评论补抓、缺口与质量补抓 |
| 数据 | SQLite 事实表，删除或受限内容与有效内容边界不清晰 | 保留占位记录，明确有效帖子、异常值、完整月份和抓取快照定义 |
| 分析 | SQL 直接导出月度总量和全局 Top 20 | 独立聚合库、schema v37、时间序列、排名、关联数据、代表内容和离线观察 |
| 前端 | 简单列表与基础图表 | 概览、帖子、成员、互动、观察五个主板块及多层详情联动 |
| 性能 | 页面直接加载少量固定 JSON | 年度分片、64 路哈希详情分片、索引先行、按视图加载、ECharts 延迟加载 |
| 交付 | 开发页面 | Vue 静态构建、Nginx、Docker、预压缩 Gzip、缓存策略、线上部署 |
| 质量保障 | 很少 | HTML fixture、抓取状态、源数据基线、分析 schema 验证、构建预算、桌面/移动端 E2E 与 Axe 检查 |

当前数据覆盖帖子 ID `1..1238527`；完整分析月内包含 1,204,199 条有效帖子和 17,523,315 条评论，成员表另有 248,043 条档案记录；看板覆盖约 25.0 万位至少发过帖子或评论的参与用户。分析时间始于 2010-04，默认只使用截至 2026-08 的完整月份。

## 3. 主要建设阶段

### 3.1 先修数据入口，而不是先画图

最初通过日志和数据库交叉检查发现，已有记录并不等于完整记录：主题可能只保存了首页评论，节点或标题可能为空，登录可见页面可能被当成不存在，停止爬虫时还有批次未落库。随后完成了：

- 从仓库外 Cookie 文件加载登录状态，并保留代理和并发配置。
- 将主题、评论改为幂等更新，重复抓取不会因主键冲突丢失新值。
- 根据页面回复数与数据库评论数判断是否补抓后续分页。
- 支持 `topic_ids=1-10,20,30-40` 形式的离散补抓。
- 通过 `backfill_missing_topics.py` 分别定位 ID 缺口和空节点/空标题质量问题。
- 将任务参数和关闭原因写入 `crawl_run`，将帖子最近 HTTP 状态写入 `topic_fetch_state`，避免再从日志文本猜测抓取是否完成。
- 对“页面回复数高于已存评论数”分级审计；高置信缺口强制遍历全部评论分页，修复中间页缺失，而不是假定已存评论连续。
- 批量提交失败后回滚，关闭爬虫时刷新剩余缓存和 HTTP 状态日志。

这一步决定了后续分析的可信上限。论坛分析不应把“爬虫跑完”视为“数据完整”。

### 3.2 从直接 SQL 导出转为离线分析层

原来的 `analysis/main.py` 将 SQL 结果直接写成几个 JSON，适合演示，不适合数百万主题和上千万评论。重构后形成了稳定管线：

```text
V2EX -> Scrapy -> v2ex.sqlite
                    |
                    v
          analysis/build_analytics.py
                    |
          analytics.sqlite + 静态 JSON
                    |
            Vue + ECharts + Nginx
```

浏览器不再扫描原始事实，也不承担大规模聚合。构建器负责清洗、统一时区、计算完整月份、生成指标和详情分片；前端只进行当前区间的轻量汇总与展示。这一架构使 5 GB 级源数据库仍可部署为纯静态站点。

### 3.3 从“总量榜单”转向动态视角

第一版看板仍偏表面，真正有信息量的变化来自时间维度：

- 概览同时呈现主题、评论、成员和互动变化。
- 月度与年度数据可以选择任意完整周期，并提供同比、环比和当期榜单。
- 话题演变按每月/每年独立 Top 10/20/30 排名，而不是拿全局 Top 固定画整段历史。
- 上升和下降使用最近 12 个月相对此前 12 个月的主题占比变化，减少全站规模波动干扰。
- 当前月不完整时不进入默认分析；当前年度只有达到足够完整月份才成为默认年度。
- 生命周期指标统一观察发布后 7 天，避免新帖子天然缺少后续回复的右截断偏差。

### 3.4 建立“结构、趋势、详情”三级分析

看板逐渐形成可复用的信息层级：

1. **结构**：所选时间范围内的总量、份额和累计榜单。
2. **趋势**：按月或年观察排名、规模和结构变化。
3. **详情**：选择话题、标题关键词、节点或成员，查看单个对象的趋势、关联数据和代表内容。

帖子板块进一步分为话题、标题关键词、节点和生命周期。成员板块保留成员演变与重点活跃成员详情；互动板块区分热门帖子和热门评论；观察页则把跨板块证据组织成可读结论。

### 3.5 从标签扩展到标题关键词

V2EX 原始标签信息质量较高，因此“话题”分析始终保留。标题分词不是替代标签，而是补充标签没有覆盖的产品名、事件和新概念。实现参考了 `/root/codes/toy/weibo/` 中群聊分析使用的 jieba、领域词典、同义词和停用词思路，并针对论坛标题重新调整：

- 同一标题中的同一关键词只计一次，指标解释为“包含该词的帖子数”。
- 区分 V2EX 原始标签形成的“话题”和标题分词形成的“标题关键词”。
- 每月/年独立计算 Top 排名、作者数、节点覆盖和相对热度。
- 生成关键词审计报告，检查头部作者/节点是否过度集中，并保留示例标题供人工复核。
- 标题关键词详情支持趋势对比、关联关键词/话题、主要节点、活跃用户和代表帖子。
- 对有限候选报告进行模型辅助只读复核，发现遗漏实体和边界异常后仍由人工回查标题、修改词表并运行校验；模型不直接处理全量标题，也不自动写入分析规则。
- 增加可选的 PKUSEG/HanLP 抽样对照，区分“当前规则遗漏”和“被停用词主动过滤”，把通用分词模型定位为审计工具，而非直接替换经过论坛语境校准的生产规则。
- 增加人工复核回归集，以 precision、recall、F1、完全匹配率和歧义约束阻止词表修改破坏已知样例；再从全量 token 中生成带频次、作者/节点覆盖和标题样例的新词候选，候选不自动进入生产词表。

### 3.6 指数与信号探索：从合成分数回到可复核事实

项目曾尝试把趋势进一步压缩为“指数”，但最终撤下了这些公开视图。这不是实现失败，而是指标验证后的主动收缩：

1. **关注指数**：将话题规模归一化到固定分值。头部话题容易长期触顶，而且与原始趋势高度重复，没有带来新信息，因此删除。
2. **就业、消费和市场指数**：曾考虑为正向/负向词赋权，再加入帖子感谢、收藏或评论证据。问题在于，标题命中“裁员”“抄底”“清仓”并不能确定立场，可能是提问、引用、反讽或交易广告；累计互动又是抓取时快照，无法对应发帖当期情绪。稀疏样本、人工权重和候选帖子偏差让最终分值难以校准。
3. **固定词信号**：随后降级为更可审计的标题精确命中，例如就业的“裁员、失业、降薪、跳槽、Offer、上岸”，按季度/年度展示并保留证据帖子。这比合成指数诚实，但本质上仍是一组人工选词，与已有的标题关键词搜索和详情趋势重复，因此也未保留为独立 Tab。

这轮探索确立了一条边界：不能因为“能算出一个数”就将它命名为指数。如果未来重启语义型专题指标，至少需要明确构念与分母、人工标注语料、按词精度/召回率、时间外验证、置信度和可回看的原帖证据。嵌入或 LLM 可以辅助标注和分类，但不能取代抽样审计。

### 3.7 产品化和上线

后期重点从“增加图表”转向可用性、性能和一致性：

- 顶层导航收敛为概览、帖子、成员、互动和观察；帖子内再按话题、标题关键词、节点和生命周期分组。
- URL 保存板块、子视图、时间范围、实体、对比项、排序和页码，并严格使用白名单解析。
- ECharts 统一折线图和热力图的颜色、图例、悬停、缩放与移动端行为。
- 搜索覆盖话题、标题关键词、节点和部分活跃成员；详情选择器支持搜索和站内跳转。
- 数据、ECharts 和异步视图按需加载，详情只读取一个哈希分片。
- Nginx 对哈希资源使用一年 immutable 缓存，对动态 JSON 使用清单版本和短校验缓存，并启用 Gzip。
- Docker 仅暴露 `127.0.0.1:3090`，由宿主机反向代理；百度统计作为服务器专用构建资产，不进入 Git。

## 4. 最有价值的功能

### 完整周期控制

这是最基础也最容易遗漏的能力。1970 年数据来自零时间戳，不是早期社区活动；进行中月份的数据天然不完整；生命周期还需要独立的观察窗口。把“数据覆盖到哪里”和“分析默认截止哪里”分开，显著减少了误读。

### 各期排名热力图

话题、标题关键词和成员都存在明显的头部更替，各期 Top 热力图比几十条折线更适合观察“谁在何时进入头部”。成员 Top 20/30 会产生大量只出现一期的账号，信息密度反而下降，因此名单演变最终固定为发帖/评论 Top 10，并取消缺少发生时间的感谢演变。集中度另以匿名聚合后的 Top 10/50/100 发帖、评论贡献占比呈现核心、扩展和较宽头部，不扩大成员详情候选。实体详情仍用折线图跟踪固定对象，用年度 Top 10 方向矩阵呈现活跃成员参与话题、标题关键词和节点的变化。

### 话题与标题关键词双轨分析

标签稳定、精确但受用户标注限制；标题关键词覆盖更广但噪声更高。两者并存可以互相校验：话题适合长期结构，标题关键词适合发现新产品和事件。对其他论坛也应优先利用版块、标签等结构化信号，再用分词或模型补充，而不是一开始就做全量 NLP。

### 对象详情与站内联动

汇总图只能指出异常或趋势，详情页面负责回答“由哪些帖子、节点和成员推动”。话题、标题关键词、节点和成员之间可以站内跳转，并保留主要对象的关联数据。代表帖子和评论让分析结论能够回到原始语境核查。

通过趋势点查看代表内容时，候选数据必须使用相同的时间粒度：年度点可以使用实体内年度 Top 10，月度点不能从年度或全部历史候选中二次过滤，否则活跃月份会大量为空。话题、标题关键词和节点的月度代表帖子与评论因此独立计算，并根据当月相关帖子数保留 Top 3、Top 5 或 Top 10，阈值分别为 20 和 100，再拆成延迟加载分片，在事件解释能力和静态数据体积之间取平衡。评论按所属帖子的发布时间归期，避免与趋势横轴口径错位。主序列使用空心时间点提示可查看，选中后变为实心，再次点击恢复整个时间范围，避免额外按钮占用空间。

### 月度与年度数据

单独的月度/年度视图比在折线图上隐藏一个点击入口更清晰。任意周期都能查看当期指标、热门话题、热门标题关键词、热门节点、代表帖子和评论；帖子按综合、收藏、感谢或点击排序。这是论坛运营复盘最容易复用的页面结构。

### 离线观察

观察页不是实时调用 AI，而是构建时生成带数字证据、可信度、背景事件和看板链接的点评。它展示了更可靠的分析写作方式：先给事实，再给解释，最后明确限制；外部政策事件只作为背景，不把同步变化直接写成因果关系。

## 5. 关键指标说明

### 最大 ID 不等于帖子数量

主题 ID 中存在删除、登录可见、权限受限、从未公开或抓取失败的记录。最大 ID 只说明编号上界，不能推导有效主题数量。更可靠的模型应至少区分：有效内容、确认不可访问的占位记录、待重试失败和完全缺失 ID。

### 快照指标不等于事件流

点击、收藏、感谢和投票是抓取时累计值，没有“何时发生”的事件时间。按帖子发布时间汇总只能解释“某时期发布的内容最终积累了多少反馈”，不能解释为这些互动发生在对应月份。要研究互动变化，必须定期保存快照并计算增量，本项目暂未建设这条流水线。

### 多标签占比不能相加

同一帖子可以携带多个话题，也可以进入多个人工话题板块。因此各板块覆盖率允许重叠，不能相加为 100%。话题同义词可以合并写法，但不应把宽泛人工板块伪装成原始话题。

### 排名需要最小样本和绝对量

早期“增长最快节点”曾出现 Apple TV、输入法等小体量节点，百分比很高但分析价值有限。最终同时设置当前量、历史量和净增门槛，并在结果中保留绝对数量。所有增长榜都应防止小基数主导。

### 异常值要隔离而不是静默改写

账号 `usdc` 的感谢值明显异常。处理方式是从累计感谢榜排除，并在说明中公开统计规则；数据库原始值和全局汇总仍保留。感谢缺少发生时间，因此也不用于按期成员演变。异常治理应可追踪，不能直接把值改成零。

## 6. 主要踩坑与修正

| 问题 | 原因 | 最终处理 | 可复用经验 |
| --- | --- | --- | --- |
| 1970 年出现在图表中 | 缺失时间用 `0` 保存 | 分析层过滤早于社区起始时间的数据 | 时间字段必须验证业务下界 |
| 进行中月份造成断崖 | 把不完整周期与完整周期直接比较 | 默认截止最近完整月，进行中周期不进入选择器 | 所有周期分析都要处理右截断 |
| 最大 ID 与有效帖子数不一致 | ID 稀疏、删除、权限和失败状态混合 | 保留占位、检查缺口、单独统计有效记录 | ID 空间不能替代事实数量 |
| 已抓主题缺少后续评论 | “存在即跳过”忽略分页和新增回复 | 比较页面回复数与已存评论数，支持强制刷新 | 增量抓取必须按子资源完整度判断 |
| 评论条数相近仍缺中间页 | 用已存条数推算分页起点，默认历史评论连续 | 强制补抓时从第 2 页遍历全部分页，以评论 ID 幂等更新 | 行数不能证明分页连续，修复任务应偏向完整重放 |
| Cookie 失效时大量空结果 | 403/302 与真实不存在混淆 | 外部 Cookie 文件、日志审计、有限范围验证后再放量 | 先验证身份状态再做大规模补抓 |
| 话题热力图展示全局 Top | 固定词表不能反映每期热点 | 每期独立排序，再组成热力矩阵 | “趋势 Top”与“各期 Top”是两种问题 |
| 折线颜色重复、交互不一致 | 自绘图表和零散配色不断累积 | 统一 ECharts、主题色板和图例行为 | 可视化基础设施应尽早统一 |
| 自制悬停导致页面卡死 | 高频 DOM/高亮更新成本过高 | 使用 ECharts emphasis/dispatchAction，并限制动画 | 复杂图表交互交给成熟引擎 |
| 分词出现“无法、收个、一款、版本”等泛词 | 通用停用词不适配论坛标题 | 领域词典、同义词、停用词和人工审计迭代 | NLP 结果必须回看原始标题 |
| “标题特有”“差异关键词”难以解释 | 为制造差异而设计复杂排名 | 删除派生概念，只保留可解释的标题关键词 | 指标定义说不清就不应上线 |
| 标题关键词与标签高度重叠 | 两者都在描述帖子主题 | 明确话题=原始标签、标题关键词=标题词，并各司其职 | 先定义语义边界，再设计页面 |
| GPT 与具体版本同时占榜 | 把展示去重误做成分词源头合并，丢失版本变化 | 主榜按关键词组聚合，GPT-4/GPT-5 等子词保留详情与搜索 | 展示层归并不能破坏底层分析粒度 |
| 关注指数触顶且与趋势重复 | 固定区间归一化只改变了尺度 | 删除指数，直接展示可解释的帖子数和趋势 | 新指标必须增加信息，不只是换算单位 |
| 经济指数和固定词信号失真 | 标题匹配无法判断立场，权重难校准，又与标题关键词搜索重复 | 撤下公开视图，保留审计经验 | 语义指标需要标注数据、样本外验证和原文证据 |
| 代表帖子数量突然膨胀 | 候选集合和详情筛选规则反复变化 | 固定候选来源、过滤推广节点、分页展示并写明规则 | 排名必须解释候选集，而不只解释分数 |
| 小卡片和三栏榜单样式反复 | 每个页面局部实现相似组件 | 抽取 RankedColumns、搜索选择器、分页和导航组件 | 同类信息应共享视觉语法 |
| 页面信息越来越散 | 按新增功能追加 Tab | 收敛顶层板块，再按实体和任务分组二级导航 | 信息架构要围绕用户问题而非数据表 |
| 单一 JSON 和 JS 首包过大 | 所有历史与详情一次加载 | 年份分片、索引/详情分离、64 路哈希、异步视图和图表运行时 | 静态站点同样需要数据 API 设计 |
| 切换时间后详情仍是旧数据 | 异步请求完成顺序覆盖新状态 | 将范围纳入加载键并防止过期渲染 | 所有异步结果都要绑定请求上下文 |
| 移动端搜索结果无法滑动 | 弹层滚动和触摸事件冲突 | 设置独立滚动容器并加入触控 E2E | PC 鼠标可用不代表移动端可用 |
| URL 状态可能接收任意输入 | 查询参数直接进入页面状态 | 枚举、范围、长度和实体白名单校验 | 可分享 URL 仍是外部输入 |
| 重建容器后统计脚本失效 | 统计文件只存在旧容器，CSP 又限制外域 | 使用服务器专用 Dockerfile 同时注入脚本与 CSP | 服务器特有配置也要可重复部署 |

## 7. 性能架构中可复用的设计

### 用分片模拟静态数据 API

静态部署不意味着只能有一个大 JSON。当前采用三类分片：

- **时间分片**：月度数据、年度数据、活跃时段、话题、标题关键词和节点趋势按年份拆分，适合范围查询。
- **哈希分片**：话题、标题关键词、节点和成员详情按稳定哈希拆为 64 片，适合按实体读取。
- **索引与详情分离**：选择器先加载轻量名称/计数索引，真正选中后才读取详情。

这种模式无需后端 API，也能控制首屏、切换视图和详情查询的数据量。分片必须配套 manifest，记录 schema、文件大小、源库指纹和组件生成时间。

### 增量构建不等于合并旧 Top N

直接把新月份 Top N 与旧榜单合并会漏掉长期累计但单月未入榜的候选。早期 `--if-changed` 为确认数据是否变化，仍需扫描百万帖子与千万评论；现在由源库触发器维护与分析相关的组件修订号，首次建立基线后可以常数时间判断是否需要重建。只有评论/成员变化时复用帖子相关产物，帖子、schema 或词表变化时重建依赖项。

标题 token 缓存也从“配置指纹变化即全量清空”改为保存语义快照：词典、同义词或停用词修改后，只重算标题中包含受影响词的记录；引擎或缓存 schema 变化才全量失效。聚合过程仍从完整 token 事实计算排名，并将标题关键词的全量源表遍历从三次减少为两次、延迟读取最终代表帖子。优化的是变更发现、分词和 I/O，不牺牲全局 Top 排名的正确性。

### 把预算变成测试

性能不能只靠主观感受。项目为主应用、ECharts、全部 JS、CSS 和最大 JSON 分片设置 Gzip 预算；Playwright 记录实际网络请求，验证详情页不会误加载全量趋势文件。生产环境再验证 `Content-Encoding: gzip`、immutable 缓存和资源哈希。

大 JSON 不应只依赖 Nginx 首次请求时现场压缩。镜像现在预生成 `.gz` 并通过 `gzip_static` 直接发送；话题与标题关键词按期帖子扩为 256 片，节点趋势和概览活跃时段从单文件改为年度分片。生成 JSON 已从源码 Git 中移出，改由 manifest 驱动的 Release 归档、锁文件、SHA-256 和原子安装独立交付；代码提交不再反复携带约 490 MB 数据差异。部署镜像使用 Git 短版本标记，同时验证首页、manifest 和详情分片；新版本不健康时自动恢复上一镜像。

## 8. UI 与交互经验

- **默认值就是产品判断**：默认近 5 年按月、结束于最新完整月份；话题与标题关键词各期排名默认 Top 20，固定对象趋势默认 Top 10，成员演变固定 Top 10。默认值应兼顾信息量、图表高度和移动端可读性。
- **同类问题保持同一种图形语言**：话题、标题关键词和成员的各期排名使用热力图观察更替，固定对象使用折线图观察连续趋势，结构排名使用统一榜单组件；相同语义保持配色、尺寸和交互一致。
- **详情必须可到达也可分享**：点击图表或榜单进入实体详情，URL 可恢复选择与对比项；外链保留回到 V2EX 原页面的能力。
- **不要为功能数量保留低信息视图**：数据质量 Tab、评论到达曲线、长尾变化、意义不清的“讨论充分”等功能都曾被删除。删掉不能支持明确问题的图，比继续装饰它更有效。
- **榜单必须分页而不是无限变长**：热门帖子、热门评论和代表内容最多保留较大候选集，但页面默认只展示 10 条并提供数字页码。
- **移动端需要独立验证**：标题范围压缩、导航换行、弹层滚动、按钮对齐和图表宽度都使用真实移动视口检查，不能只依赖 CSS 推断。

## 10. 做类似论坛分析的推荐顺序

1. **定义事实边界**：列出主题、回复、用户、标签、版块、互动值及其时间语义。
2. **抽样核查页面**：对正常、删除、登录可见、分页、多标签和零回复页面分别验证解析。
3. **建立状态模型**：区分有效、不可访问、失败待重试和缺失，不把所有异常都写成零。
4. **先补可靠性**：实现幂等写入、日期边界验证、断点续抓、缺口扫描、任务状态、验收报告和 Cookie 失效检测。
5. **确定完整周期**：处理时区、零时间戳、当前月和生命周期观察窗口；月末累计快照应在成熟窗口后统一刷新。
6. **先做概览和周期数据**：帖子、回复、用户、互动总量，以及任意月或年度的结构榜单。
7. **优先利用结构化分类**：版块、节点和标签通常比直接 NLP 更稳定。
8. **再补标题关键词分析**：从标题开始，使用领域词典和审计报告，并从真实标题分层抽样建立人工回归集；正文和评论语义留到确有问题需要时。
9. **建立对象详情**：趋势必须能回到代表帖子、评论、用户和关联数据。
10. **设计静态数据契约**：索引、时间分片、哈希详情、manifest、schema 和缓存策略一起规划；重构前先量化重复数据与请求开销。
11. **统一交互和图表**：使用成熟图表库，建立固定颜色、图例、分页和搜索组件。
12. **边做边删**：每个视图都回答一个明确问题；无法解释或样本不足的指标不上线。
13. **加入质量门禁**：单测、数据验证、浏览器测试、性能预算和线上冒烟缺一不可。
14. **最后写观察**：区分事实、解释和背景，不用时间同步代替因果证据。

## 11. 参考与技术选择

- 原始爬虫和数据模型来自 `oldshensheep/v2ex_scrapy`，避免重写已成熟的基础能力。
- 微博群聊项目 `/root/codes/toy/weibo/` 提供了中文分词、时间演变和内容审计思路，但本项目按论坛标题、标签和节点结构重新建模，没有直接依赖其代码。
- Scrapy 负责抓取调度，SQLAlchemy/SQLite 保存事实，Python 离线构建聚合，Vue/Vite 实现交互，ECharts 负责专业图表，Playwright/Axe 负责浏览器和无障碍验证，Nginx/Docker 负责静态交付。
- 社区制度事件只采用可核查来源。例如邀请码制度使用 V2EX 官方主题作为背景证据，并明确“时间断点吻合不等于唯一因果”。

## 12. 有意暂缓的方向

- **互动指标快照流水线**：需要定期重抓同一内容，才能获得收藏、感谢和点击的真实增量时间。
- **正文和评论语义分析**：成本和误判风险远高于标题；在没有明确问题前，不宜为“更智能”而增加情感或主题模型。
- **语义型专题指标**：关注、经济指数和固定词信号均已验证后撤下；只在具备标注样本、明确构念和样本外评估时重启。
- **全量成员画像**：公开行为分析也应遵守最小必要原则，目前只覆盖有限活跃成员且不推断个人属性。
- **成员留存队列**：有分析价值，但注册数据完整度、身份边界和页面空间尚不足以支撑可靠呈现。
- **自动更新流水线**：当前明确暂缓；上线前仍采用人工抓取、验证、构建和部署闭环。
- **严格因果分析**：邀请码等事件可以作为解释背景，但当前数据和设计不足以排除其他同期因素。

## 13. 最终经验

1. 数据产品的可信度首先来自抓取状态和清晰的指标定义，而不是图表数量。
2. 论坛分析最有价值的是动态变化和可追溯的原帖证据，而不只是累计 Top 榜。
3. 标签、标题、正文和互动分别代表不同信号，不能混成一个“话题”指标。
4. 当前周期、快照指标、多标签和小样本是最常见的四类误导来源。
5. 静态站点也应像 API 一样设计数据契约、分片、版本和缓存。
6. 专业图表库能解决性能、颜色、图例和移动端交互的一致性问题。
7. 默认范围、默认 Top 数量和信息架构比增加高级算法更影响实际可用性。
8. 所有聚合结论都应能回到代表帖子或评论核查。
9. 低信息功能应及时删除，避免看板成为指标陈列柜。
10. 合成指数只有在构念、方向、分母和验证样本都清晰时才值得上线，否则原始趋势更诚实。
11. 可复用的最终产物不是某张图，而是一套从数据审计到线上验证的工程闭环。
